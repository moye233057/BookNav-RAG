## 产品边界

## 工业级 RAG 为什么默认「向量 + 关键词」，而不是纯向量？

### 1、问题背景

很多教程把 RAG 画成：embedding → 近邻 → 拼 prompt → 生成。开源产品里更常见的是向量近邻再加 BM25（或词项引擎），两路融合。有的系统主路径只有向量。面试会问：到底要不要关键词路。

### 2、原因

双塔向量比的是语义近。近义词、换说法能召回，但专名、型号、短操作词、用户原话里的关键词不一定近。BM25 比的是词面共现：手册标题、零件名、步骤用词对得上就排前，但同义改写会漏。只走一路，另一路擅长的 query 会系统性失败。库变大以后，纯向量还有近邻挤在一起、ANN 近似漏检的问题。

### 3、解决方案

两路召回，再用与分数量纲无关的方法融合（常用 RRF：按各路名次加 `1/(k+rank)`，不必把余弦和 BM25 原始分强行对齐）。过滤（来源、标签）两路共用。最终进生成的条数仍要截断，但截断发生在融合之后，必要时再精排。

### 4、这样做的目的和效果

覆盖「意思近」和「词对得上」两类问法，召回更稳。融合分只表示排第几，不能当「有多相关」用。

## 开源 RAG 产品目录很全，怎么判断该学哪一层？

### 1、问题背景

成熟产品仓里同时有解析微服务、队列、权限、Agent 画布、图检索、评测台。对照时容易把「别人有的模块」当成自己系统的缺口。

### 2、原因

那些仓多数是**知识库产品**：任意文档入库、多租户、工作流。RAG 问答只是对话里的一段。解析、队列、RBAC 解决的是平台问题，不是「这一问检索准不准」。Agent / 图检索在多数仓里也是旁路，不是混合检索的下一层。把产品层抄进问答系统，会换一套身份。

### 3、解决方案

先画自己的主路径：离线（解析 → 分块 → 索引）和在线（问句处理 → 召回 → 精排 → 生成 → 引用）。对照时只问：这一层是否提高**召回、精排、忠实度或可测性**。平台能力（登录、队列、管理台）和主路径 Agent 分开看，需要再做，不需要就不做。同名组件也要拆开：都用某嵌入式向量库，有的仓纯向量，有的仓向量+BM25，学的是检索公式不是库名。

### 4、这样做的目的和效果

优化落在检索质量，而不是把问答系统做成平台。面试里能说清「RAG 引擎」和「RAG 产品」不是同一张架构图。

## 问答主路径为什么不要接 Agent / 工具循环？

### 1、问题背景

检索很像可以做成 Tool：模型自己决定要不要搜、搜几次。面试会问：RAG 是不是 Agent 的一种。另一边，在线路径上常留着改写、精排、精确匹配短路等开关，容易把主路径也做成「模型当时选哪条」。

### 2、原因

RAG 主路径是确定性步骤：分类 →（可选）召回 → 组提示 → 生成。每一步的输入输出是固定对象（查询、命中、生成结果）。闲聊用条件边跳过召回，仍然是固定拓扑，不是模型选工具。Agent 是模型选工具、可能循环：闲聊、拒答、引用形状都会变成「当时怎么选」，同一问句评测对不上。插件（改写、精排、精确匹配）若改写入参形状，关掉之后主路径对象就断了。

### 3、解决方案

主路径用图或函数链串层，生成用 `prompt | model | parser`。检索不是 Tool。闲聊走条件边，不走「模型决定搜不搜」。改写、精排、精确匹配只在启用时接入；启用与拆卸使用同一套查询 / 命中 / 生成结果。Agent API 只放学习旁路，不接提问口。

### 4、这样做的目的和效果

同一问句可复现。引用、拒答、闲聊走固定边。面试里能分开「检索后生成」和「模型选工具」，也能分开「主路径合同」和「可拆插件」。

## 离线：抽取与分块

## 抽取层为什么不能做成「每种格式一个适配器」？

### 1、问题背景

离线入库要吃的格式可能很多（PDF、Office、网页、纯文本）。常见画法是一种扩展名一个解析器，再为第一种样本写一条从文件干到向量库的脚本。面试会问：扩 Office 或 HTML 时该不该再开一个适配器。

### 2、原因

格式是输入形态，不是抽取策略。同一份 PDF 可能走「有印刷目录的手册解析」，也可能走通用多模态解析（扫描件、内嵌图）。Office / URL 往往共用后者，并不需要本仓再实现一套 Office 解析。把第一种样本的完整入库脚本当成抽取层，层边界会变成「这份样本」，扩源时只能复制整条管道。

### 3、解决方案

抽取层按步骤拆：先认文件基础信息（路径、大小、扩展名），再按规则选抽取方式，方式只吐文件内容（有页则页列表，无页则正文；目录区间可选）。方式可插拔：增删靠登记表，不扫目录自动发现。方式不准写最终原文对象、不准抽过滤标签、不准分块、不准 embedding。某种手册解析是其中一种方式，不是抽取层本身。通用格式不在本仓实现，也不接外仓 RAG 抽取口：手册 PDF 抽页已收回本仓（ADR-0034），路由只登记 PDF，非 PDF 在路由被拒，外仓 `/rag/extract/file` 已下线。

### 4、这样做的目的和效果

扩源是加方式或改路由，不是再堆格式适配器。拆卸一种解析不必动分块和索引。面试里能说清「输入种类」和「怎么抽」是两件事。

## 抽取为什么必须停在一份形状固定的原文，而不是一条脚本从文件干到向量库？

### 1、问题背景

能跑的入库脚本常常是：抽页 → 切块 → embedding → 落盘，一个入口走完。看起来少一次磁盘跳，也少一个模块。

### 2、原因

抽取、分块、索引失败原因不同：解析烂是正文空或页码错；分块烂是切太碎或丢掉标题；索引烂是向量服务或落库。焊在一条脚本里，换解析方式必须重跑 embedding，测解析也要起模型服务。下游（分块、可选的精确匹配旁路）需要同一份「可切的原文」：正文、可选页、可选目录、文档身份。解析器若直接吐知识块，页码和切法被锁死，引用和第几页对不上。

### 3、解决方案

抽取层的产出合同先钉死：文档身份、类型、页列表或无页正文，可选目录区间。分块只读这份对象。两层用磁盘上的这份对象相接，不互相 import 入口。人对库跑入库时再串「抽取 → 索引」，那是编排，不是把两层写回一个包。

### 4、这样做的目的和效果

解析可单测到原文，不必 embedding。换手册解析或通用解析，索引合同不变。旁路（FAQ / 精确匹配）也吃原文，不吃切好的块，避免和向量库双写两套切法。

## 过滤标签为什么必须在抽出正文之后生成，不能用文件名冒充？

### 1、问题背景

源文件名里常带品牌、课号、合同号。入库图省事会把文件名写成过滤字段，或在抽取前手填常量。检索时问句点名该字段，过滤看起来「总能筛到」。

### 2、原因

文件名是文档身份（来源），不是知识内容。改名、一份文件含多个属性、英文文件名单写中文标签，都会让标签撒谎。过滤按标签硬切，假标签会把该命中的块切掉，或把不该命中的留下。标签是「正文里出现过什么」，只能在有正文之后由模型或规则从摘录抽出；抽不出就空，让查询侧不误加过滤。

### 3、解决方案

先抽文件内容，再从正文摘录生成标签。来源仍用路径 stem 或 URL，禁止用文件名回填领域属性。生成标签的步骤不进解析方式内部：方式可替换，标签步骤仍吃「正文摘录 + 文档身份」。不要把来源再写成一条过滤标签。

### 4、这样做的目的和效果

过滤和文档真实内容对齐。换解析方式不必重写打标签。空标签比错标签安全：宁可不筛，也不切光。

## 「页归进目录标题」为什么放在分块层，而不是解析层？

### 1、问题背景

分页 PDF 能抽出页和印刷目录区间。有人在解析阶段就把每页打上章节标题，有人把「归页」函数留在解析模块里给分块调用。面试会问：解析和分块的边界在哪。

### 2、原因

抽取方式的合同是文件内容：有页则页列表，目录区间可选。它不管怎么切成检索单元。按标题拼知识块、丢掉目录/索引页、超长再切段，是「可分块原文 → 知识块」的策略，属于分块。解析模块若把归页 export 给索引层 import，两层互相踩对方内部函数，换解析方式时分块跟着烂。

### 3、解决方案

解析只吐页列表和目录区间。分块读取这两样，在索引层内做归页再拼块。两层只通过磁盘上的可分块原文相接，不互相 import 入口。解析器页码若从 0 起，写入知识块、给人看的引用之前要换成从 1 起，否则侧栏页码和阅读器对不上。

### 4、这样做的目的和效果

换解析方式时，分块策略仍认同一份原文形状。解析测试不必跑 embedding。OCR 改的是页文本，仍在解析方式里，且应在合同稳定后做。

## 层合同没钉死时，为什么不要先做 OCR、热加载、改字段名？

### 1、问题背景

系统已经能入库、能问。待办上还有：图 OCR、入库后问答进程不用重启、把 JSON 字段改成「更干净」的名字。都像能立刻开工的功能。

### 2、原因

OCR 是某一种抽取方式内部的增强，热加载是进程怎么读库，改字段是入库、召回、生成、前端 schema 的共用合同。层职责（抽取停在哪、分块算哪层、过滤是不是图节点）没钉死时，这些改动叠在糊边界上：OCR 往哪一层写正文、reload 重载的是哪份对象、解析还写旧名、召回读新名。结论站不住。

### 3、解决方案

先定层和模块清单，再按现码写输入输出（字段名先不动）。离线从抽取收到向量，在线从意图收到生成。边角（OCR、热加载）和「怎么更准」列成槽或未来实验，不和收口边界混在一刀。要改合同时另开对照实验。

### 4、这样做的目的和效果

每一刀改的是边界，不是装饰。调参时样本对着的是同一套对象。真正换字段时，输入输出表就是迁移清单。

## 离线：索引与存储

## 分块、embedding、写入向量库为什么算一层？模型 HTTP 服务为什么又不是这一层？

### 1、问题背景

教材把离线画成解析 → 分块 → 向量化 → 存储四段，于是仓库里四个目录。向量化又常和「起一个 embedding HTTP」写在一起。在线提问也要把问句编成向量。

### 2、原因

对知识库来说，分块、调用 embedding、upsert 是同一件事的后半截：把可分块原文变成可搜的向量库。拆成三层后，层与层只有单次串联、没有第二处复用，目录在假装架构。但 embedding **模型进程**同时服务入库（块）和在线（问句）。把它放进离线包，在线召回会 import 离线目录，或复制一份客户端。问句和文本块若打两个不同的 embedding 口，近邻比的就不是同一空间。字符散列占位向量能打通入库，但不能当语义检索。

### 3、解决方案

离线后半截收成索引/向量层：读可分块原文，内部分块、HTTP 调 embedding、写入向量后端（及并列的词面倒排）。模型服务单独成共享进程：不属于离线、也不属于在线。索引层只当 HTTP 客户端。入库块和问句打同一个服务、同一个模型与维数。Hash 等占位向量只给打通路用，线上检索用语义 embedding。

### 4、这样做的目的和效果

换解析不影响怎么索引；换向量库只改索引层落盘。问句和文本块空间一致。重启模型服务不必假装在「离线模块」里。

## 人对库的入库命令，为什么是独立脚本串两层，而不是每个层自己带入口？

### 1、问题背景

拆完抽取和索引之后，容易在两层各留一个可执行入口，再加一个「只测抽取」的脚本。三个入口都能往磁盘写，分不清哪个是入库。层目录里还会留下只给人单测、流程并不调用的文件。

### 2、原因

层入口回答「这一层吃什么、吐什么」（函数）。入库回答「人怎么把一份文件送进知识库」（编排）。两个问题焊在层包的可执行入口里，调试开关会漏进生产模块。两层各带 CLI，失败时不知道该重跑抽取还是索引。测试专用文件放在层目录，读代码的人会当成主路径。下载权重、评测、一次性调试和长驻 HTTP 也不是同一类入口。

### 3、解决方案

层模块只提供函数，不要可执行入口。人对库一条入库脚本：按份先抽取再索引。层目录只留流程会调用的模块；单测和全路径测试放脚本目录。长驻服务另有进程入口。下载权重、评测与入库同类：跑完即退出，不占端口。

### 4、这样做的目的和效果

使用说明只教一条入库命令。测解析不必起 embedding；正式入库仍走同一套函数。层目录保持可插拔，不被调试入口污染。

## 向量存在 JSON 里够不够？什么时候换成嵌入式向量库？

### 1、问题背景

第一版常把每条知识块的向量写成一份 JSON。几百到几千块时，启动读进内存、Python 暴力余弦也能答。面试会问：这还算不算向量库？要不要上独立搜索集群。

### 2、原因

JSON 是记录列表，不是检索引擎：没有列过滤下推、没有 ANN、整库 float 当文本读写。库小、重启可接受时，足够打通「分块 → embedding → 近邻」。痛点出现在：过滤要先扫全表再算相似度；落盘和启动随维数线性变贵；多进程不能安全同写一份文件。嵌入式库底层仍是磁盘上的目录或文件，禁的是**应用自己写的 JSON 当权威库**，不是追求磁盘零文件。源文档和权重本来就该是文件。

### 3、解决方案

本地、不另起进程：用嵌入式向量库（表里同时有向量和 payload）。调用方仍按来源替换写入。BM25 可以仍进程内，不必上独立词面引擎。没有碰到过滤下推或规模问题之前，JSON 可以打通链路；一旦过滤和启动成本成为痛点，换的是后端，不是检索对象。调试 JSON 可以留着对照，问答启动不应再扫它们当库。

### 4、这样做的目的和效果

小数据能答；真要库时换的是引擎，不是公式。面试里能把「文件里的 float 数组」和「可过滤的向量表」分开，也能把「权威库」和「磁盘上的资产 / 日志」分开。

## 为什么不能默认「本地嵌入式、线上必须某集群向量库」？

### 1、问题背景

选型时容易画成两套：开发机嵌进 Python 的库，生产上某开源产品常用的集群引擎。代码里预埋双后端，调用方写一层抽象。

### 2、原因

线上用什么库看运维，不看名字。单机一个进程往往更省；已有关系库用向量扩展少一套系统；要对齐某产品仓的三件套才是集群引擎加协调服务加对象存储，常再加词面引擎。数据没到需要集群的量，嵌入式库也可以当生产。预埋「本地 A、线上 B」等于每条写入和查询维护两套语义，过滤、upsert、维数检查都会分叉。抽象层解决不了「两套引擎的 where 和距离定义不一样」。

### 3、解决方案

调用方只认一种写入（按 id 或按来源替换）和一种近邻+过滤。先换一个能在本机跑的嵌入式后端。没有集群、多租户、运维编制，不要上重型引擎。真要独立服务进程，优先单进程引擎，而不是「因为产品仓用过所以预留」。

### 4、这样做的目的和效果

一套检索公式、一套落盘。避免面试答成「本地玩具库、线上换名字就算工业级」。

## 知识块正文要不要放进关系库，向量库只存 id+向量，查询再 JOIN？

### 1、问题背景

换成向量库之后，会想到：向量是近邻用的，正文、页码、标签是结构化的，关系库更「正规」。检索时先 ANN 拿 id，再 SQL 取 text。

### 2、原因

生成要的检索命中必须带正文和出处。正文若只在关系库，每问多一次按 id 取数，入库还要双写。没有管理后台按主键改块、没有多表事务、没有用户账号时，动态标签、页列表在向量表里就是列或 list。可分块原文只给切块用，问答不搜它，不必为了「消灭 JSON」先上第二库。

### 3、解决方案

问答路径的权威行：id、text、来源、页、标签、vector 同表。关系库只在真有按主键改、约束、或多表 JOIN 时再开。源文件和模型权重永远是文件。

### 4、这样做的目的和效果

一问一次近邻就能带上生成所需字段。不为「可能更合理」付双写和两套迁移。面试能说清：向量库不是只能存 float。

---

## 多来源是「每本书一个向量表」，还是一张表、来源当列？

### 1、问题背景

离线常按来源分目录写抽取结果。换成库以后，直觉是每本书一个 collection / 一张表，和目录一一对应。

### 2、原因

产品问题是「一份逻辑知识库，按来源/标签收窄」，不是「打开哪本手册的库」。每来源一张表：召回要扫所有表或先选表；跨来源问句要自己做合并；维数和 embedder 一致性检查分散。一张表、来源当列：替换写入是删除该来源再写入；过滤是 `where`；逻辑库就是这张表。领域属性同样是列或标签，不是库边界。

### 3、解决方案

检索知识块一张表。重入库同一来源先删该来源再写，避免切块规则变了留下旧 id。抽取产出仍可按来源分目录（中间物），不要把目录切法复制成表切法。

### 4、这样做的目的和效果

过滤和跨来源检索是同一套查询。物理目录可以按文件走，逻辑检索按列走。

## 向量表改了过滤列或 embedding 维数，为什么不能在旧数据上继续搜？

### 1、问题背景

过滤从两列固定字段改成一列标签列表。或换了 embedding 模型。代码按新 schema 读写。盘上已有旧向量文件，想写脚本转进去，避免重跑 embedding。

### 2、原因

嵌入式向量表通常一行同时存向量和 payload。旧行没有新列，load 时拼不出标签；就地改列名，旧值对不上新的键值形状，过滤会 silently 错。标签来自抽取，不来自向量，不能从旧列「迁移」出来。旧落盘往往还缺后来才定的合同字段。embedding 模型或维数一变，旧向量也不能留。写转换器要维护「旧形状 → 新 schema」的分支，和重跑入库抢同一条测试路径。

### 3、解决方案

只认新写入路径：重跑抽取和入库。启动发现没有表或 schema 不对就失败，提示重建，不要用空标签把旧库先跑起来。维数或 embedder 名变更时删库再入。不要双写旧 JSON「以防万一」。

### 4、这样做的目的和效果

一条写入链路可测。过滤合同和库存数据同一版本。代价是必须能重跑抽取和向量服务。

---

## 换成向量库之后，为什么还把整库向量 load 进内存做余弦是白换？

### 1、问题背景

最小改动是：入库改成写表，启动仍把所有向量读出来，search 仍 Python 循环余弦。看起来「已经换库了」。

### 2、原因

换库要拿的是：列过滤在引擎里做、近邻由引擎算、不要把全表 float 当启动成本。若仍全量 load，过滤下推和「别当 JSON 读写」都没拿到，只换了落盘格式。启动变慢、内存仍随维数 × 块数涨。BM25 需要正文，可以只投影 payload 列建倒排，不必带上向量列。SDK 的近邻参数名随版本变，抄另一份文档会在运行期才爆。

### 3、解决方案

启动：打开表，读 id / text / 标签，建 BM25 和标签目录。提问：引擎上做近邻，距离类型在查询对象上设成余弦，过滤能下推的下推。命中只把正文和出处交给生成。换 SDK 时对着已装版本的方法签名。

### 4、这样做的目的和效果

内存跟「有多少块的正文」走，不跟「维数 × 块数」走。过滤作用在检索空间上。

## 在线：问句、历史、身份

## Query 改写解决什么问题？和多轮指代补全有什么区别？

### 1、问题背景

用户不会按文档标题提问。「车上那个镜子往里收」和手册里的「外后视镜折叠」不是同一串字。多轮里还有「那它怎么展开？」。两者都像「要把问句变得更好搜」，容易混成一件事。

### 2、原因

索引里的块是按文档用语切的。BM25 尤其依赖词面；向量对口语好一些，但短操作、代词仍漂。

- **改写**：本轮已经是完整问句，只是用词不像文档。要变成适合检索的短查询。
- **指代补全**：本轮不完整，依赖历史（「它」「那个」「呢」）。要先还原成可独立检索的句子，再检索。

只做指代，口语完整句不会变。只做改写、不看历史，多轮代词会对错对象。改写还会多一次模型调用，坏改写会伤本来就对的规范问句。补全若吃进闲聊轮，代词可能指到助手客套话。

### 3、解决方案

两段分开：完整口语句走改写；像跟进的短句走补全（只吃检索轮历史，避免闲聊轮污染）。改写结果只给检索，生成仍用用户原文，避免答案腔调被改写成「检索腔」。上线前后用同一批口语样本看 Hit@k，确认不是改坏。身份追问不要改成关键词沙拉，检索问句沿用上一轮。

### 4、这样做的目的和效果

检索问句和文档用语对齐，召回上升。付一次延迟税。改写解决「用词」，不解决「候选里谁更答得上这问」（那是精排），也不解决「窗口里只有半段步骤」（那是分块 / 父块回填）。

## 闲聊和拒答差在哪？为什么不能合成「不检索」一种？

### 1、问题背景

用户说「你好」，系统不查库、短答打招呼。用户问天气，库里是操作手册，系统应说依据不足。两者都「没有引用」，实现上容易走同一个分支。

### 2、原因

闲聊是**不该检索**：问候、问助手是谁。走召回只会浪费一次 embedding，还可能从手册里掏出不相干段落硬聊。拒答是**检索了但证据不够**：题外话仍能搜到近邻，只是不够当证据。一个发生在意图分类，一个发生在召回之后看相关度。合成「不检索」之后，题外话永远看不到相关分，正样本误伤和题外话漏网无法用同一套负样本标定。

### 3、解决方案

分类出闲聊：条件边跳过召回，生成无引用，文案是打招呼或人设，不是「知识库没有依据」。分类出检索：走召回；空命中或相关分低于阈值再拒答，文案是依据不足，引用可空。评测把闲聊样本和拒答负样本分开。

### 4、这样做的目的和效果

问候不会变成拒答官腔；题外话不会靠「没走检索」假装安全。排障时先看是分路过了还是阈值过了。

---

## 多轮历史为什么只给意图层，检索为什么不把整段对话拿去搜？

### 1、问题背景

多轮对话里，本轮只有「那它怎么展开」。直觉是把最近几轮原文拼成一个长查询再检索，或把历史也做成向量去搜。

### 2、原因

检索单元是知识块，不是对话回合。把历史原文拼进查询，BM25 会被上一轮答案里的词带着走，命中上一轮已经引用过的段，而不是本轮真正要的操作。历史的职责是**还原本轮问的是什么**（指代、沿用筛选），不是再提供一批检索词。生成若再吃整段历史当证据，会把上一轮模型自己的话当成手册。

### 3、解决方案

会话历史只进入意图：分类、改写/补全、本轮筛选。检索只针对本轮问题或改写后的短查询。生成用本轮用户原文加本轮命中（外加文档身份），不把历史当摘录。跟进补全只吃检索轮，不吃闲聊轮。

### 4、这样做的目的和效果

「它」能指向上一轮对象，又不会把闲聊或旧答案污染倒排。代价是必须持久化每轮的筛选和检索问句，下一轮才能沿用。

## 用户问「你的资料来自哪个品牌」，为什么系统会当成闲聊？

### 1、问题背景

上一轮已经在答手册操作。用户接着问资料来源、哪个品牌、哪份文档。分类器输出闲聊，助手开始自我介绍，不检索。

### 2、原因

闲聊规则通常包括「问你是谁」。问句带「你的资料」，表面像问助手身份。分类器若只看本轮字面、不看「上一轮已经检索过」，会走闲聊分支：不召回、不带过滤标签、生成也看不到文档身份。这和「你好」「你是谁」不是同一类：前者问的是**刚才那次答案对应哪份知识**，后者才是产品人设。

### 3、解决方案

分类把「问助手本人 / 什么模型」和「问刚才答案的来源、属性、哪份文档」拆开。有检索历史时，身份追问强制走检索（或走「用上一轮筛选作答」的短路），不要进闲聊提示。历史文本里应带上上一轮实际用过的筛选，分类和改写才看得到界面上已经出现过的值。

### 4、这样做的目的和效果

多轮里问出处不会变成客套话。代价是要维护「什么叫身份追问」的规则或提示，过宽会把内容问也强制检索；过窄又漏「你的资料来源于…」这种说法。

## 界面已经显示出品牌，模型却说摘录里没有品牌，缺了哪一层？

### 1、问题背景

过滤或意图已经选出文档属性，聊天气泡旁的芯片也画出来了。用户追问「刚才说的是哪个品牌」，生成只根据命中段落作答。段落是操作说明，正文没有品牌二字。模型遵守「不要编造摘录没有的内容」，属性就答不上。

### 2、原因

芯片来自**过滤合同**（入库抽出的文档级标签），摘录来自**检索命中正文**。这是两路事实。生成提示若只喂摘录，等于丢掉已经算出来的文档身份。改写若把「哪个品牌」改成操作关键词加属性词，生成面对的还是步骤段落，仍然找不到。

### 3、解决方案

生成同时看到：用户原文、文档身份（与芯片同一份标签）、摘录。规定：操作和规格只根据摘录；来源与文档属性可以用文档身份，身份里没有的不要编。改写结果只给召回。身份追问的检索问句沿用上一轮。会话轮次要持久化本轮筛选，下一轮才能沿用。

### 4、这样做的目的和效果

用户看见的筛选和模型用来答出处的依据一致。代价是 prompt 多一段身份，操作类回答可能开口先提属性，要用提示词压住「没问身份就不要念标签」。

## 问句里的属性词，为什么由意图选候选，而不是过滤层自己猜？

### 1、问题背景

库内有来源和过滤标签。用户说「某车型后视镜怎么折」。过滤层已经会按标签硬匹配。容易把「从问句抽出标签」也塞进过滤模块。

### 2、原因

过滤是**收窄集合**：给定 filters，留下匹配的块。它不理解问句、不看对话历史。从问句（和历史）对照库内目录选出「本轮用哪些值」，是分类/改写同类的问句理解，属于意图。混在一起后，过滤层既要 NLP 又要 match，闲聊跳过召回时还得特判「要不要抽标签」。

### 3、解决方案

意图：分类、改写/补全、标签候选（对照目录，没点名则该维空）。过滤：空过滤、filters 转成展示用标签、match。调用方调试覆盖 filters 时跳过候选、强制检索。没点名不要把库里仅有的那个值自动填上。

### 4、这样做的目的和效果

没点名就不误加仅有的那个属性。历史指代「它」仍由意图读检索轮历史。过滤保持纯函数，可单测。

## 在线：召回、精排、拒答

## 为什么「没检索到就拒答」仍然可能胡编？

### 1、问题背景

常见策略：命中列表为空则固定拒答，避免模型瞎编。实际题外话往往仍能搜到若干块，只是不太相关，系统照样生成。

### 2、原因

向量空间里任意问句都有近邻，差别只是远近。BM25 对任何含常用字的查询也能打出非零分。只要 `top-k` 必须填满，列表就不会空。生成模型看到「有摘录」就会尽量用，哪怕摘录答不上这问。空列表只覆盖「库空 / 过滤后为零」这一类，覆盖不了「有块但不够当证据」。

### 3、解决方案

拒答看**相关度是否够**，不看列表是否为空。要用有物理含义的分：向量余弦、交叉编码器分、或单独的相关模型。不要用排名融合分。阈值用负样本标定：正样本应生成，题外话应拒。只有词面命中、没有语义分时，不要拿缺失的余弦当弱证据去拒，要单独规定。

### 4、这样做的目的和效果

证据不足时不编。阈值过严会误伤长尾正样本，过松题外话仍生成，所以必须有负样本，不能拍一个常数长期不测。

## 为什么 RRF（或「排第几」的融合分）不能当拒答阈值？

### 1、问题背景

混合检索后每条命中有一个融合分。想「分数低于某值就拒答」，直接拿这个分做阈值。

### 2、原因

RRF 典型公式是各路 `1/(k+rank)` 求和。它只编码**名次**，和余弦、BM25 原始分都不是同一量纲。只要还剩至少一条，第一名的融合分大约是 `1/(k+1)`，恒为正。把阈值设在 0 附近等于从不拒；设在较大值又和真实相关度对不上，因为「排第一」不等于「答得上」。把向量余弦覆盖写成融合分之后，原来那条能卡远近的信息还丢了。纯词面命中没有余弦，也不能拿融合分凑一个「相关分」。

### 3、解决方案

排序用融合分，拒答用另一路分：保留召回时的向量相似度，或精排模型分。两套分不要互相覆盖。向面试官说明：融合解决的是「两路怎么合成一张表」，阈值解决的是「这张表够不够当证据」。

### 4、这样做的目的和效果

该拒的拒、该答的答，不出现「永远有分所以永不拒」。调试时能分开看：排序乱了调融合 / 精排；胡编调相关阈值。

---

## 双塔 embedding 和交叉编码器各干什么？为什么要两阶段？

### 1、问题背景

「检索不就是算相似度吗？」有人主张全程交叉编码器（问句和每块成对打分），有人主张只做 embedding 近邻。不少系统强调：一阶段 embedding 在数据变大后会退化，要二阶段 rerank。

### 2、原因

**双塔（bi-encoder）**：问句、文档各自编成向量，点积或余弦。文档向量可预计算，适合扫全库或 ANN。问句和某块没有在同一层里互看，近邻挤、易混淆（「折叠」和「展开」很近）。

**交叉编码器（cross-encoder）**：`(问句, 块)` 拼成一对再打分，准很多。每一对都是一次前向，不能扫全库。

只用双塔：排在前面的不一定是「答这问」的块。只用交叉编码器：延迟和算力随库规模线性爆炸。

### 3、解决方案

两阶段：双塔（可加 BM25）宽召回，求不漏；交叉编码器只打候选窗口，求不乱；再截最终条数给生成。候选必须够宽，精排才有东西可救。小库上收益可能不明显，库变大或近邻混淆时才显著。没有交叉编码器时，这一层仍负责截断，不要把「模型没上」理解成「召回已经是生成窗口」。

### 4、这样做的目的和效果

全库可扫、窗口内更准。延迟可控：精排条数 × 每对长度才是精排账单。面试里这就是「召回 + 精排」，不是两次重复检索。

## 为什么不能在召回阶段就截成最终 top-k，再拿去精排？

### 1、问题背景

实现上常先混合检索，直接截 5 条进 prompt。后面即使接了 rerank 模块，也只能在这 5 条里换顺序。直觉是「反正生成只用 5 条」。精排模型还没上时，更容易让召回直接截最终条数。

### 2、原因

召回的任务是**高召回**：相关块进窗口即可，顺序可以脏。精排的任务是**高精确**：窗口里谁该进 prompt。若召回已经按粗分截成最终条数，排在第 6 的相关块永远进不了精排，模型再准也救不回来。两路各取 20 再融合截 5，和「融合出 20 再精排截 5」不是一回事：前者精排输入只有 5。评测若在宽窗口上算分、线上只用前 5 条，结论是假的。

### 3、解决方案

召回（含融合）输出候选窗口，宽度明显大于最终条数（常见是几倍或至少十几、二十条）。最终条数由精排这一层负责：有交叉编码器就重排再截；暂时没有，也保持召回序只截断。所有权要清楚，召回不要提前变成生成窗口。以后换精排模型不必改召回截断位置。评测在截断之后算 Hit@k，和 prompt 一致。

### 4、这样做的目的和效果

相关块只要进了候选，就还有机会被排进 prompt。窗口过大只增加精排耗时，要另用预算卡住。

---

## 同节邻块为什么要在最终窗口截完后再并，不能从宽候选名单里再捞人？

### 1、问题背景

步骤跨相邻块时，会把「同一标题下的前后段」并进命中正文。实现上容易写错：精排还没截断，就拿召回那二十来条里同标题的块补进来；或截完 5 条之后，又从那二十条里加进新的一条。面试会问：邻块回填发生在哪一层，补的是正文还是新的命中。

### 2、原因

宽候选是给精排挑的，不是给生成看的。从宽名单再捞「新人」，等于把已经决定不进 prompt 的块又塞回去，最终条数和评测窗口都会漂。并段的目的是：已经进窗口的那几条，周围缺的步骤补进**同一条**的正文。检索命中对象还是那几条，不是召回列表的超集。标题为空时没有「同节」，硬并会把无关段焊在一起。

### 3、解决方案

先截成生成窗口（有精排模型就重排再截，没有就保持融合序只截断），再只对窗口内的命中，按同一目录标题把相邻块的正文并进去。同标题去重；空标题不并；给合并设 token 上限。不要从截断前的候选里新增命中 id。目录标题可以进索引行，不必写进对外的命中合同。

### 4、这样做的目的和效果

生成看见的条数仍然可控，步骤不容易半截。评测仍对「截断之后、并段之后」的那份列表，和线上 prompt 对齐。代价是 prompt 变长；和「加大 k」不是一件事：加大 k 是多塞几条不同命中，并段是给已有命中补邻居。

## 词重叠 rerank 和模型精排差在哪？

### 1、问题背景

重排槽有时先用查询词和正文的 token 交集排序，实现快、无额外模型。看起来已经「做了 rerank」。

### 2、原因

词重叠用的信息和 BM25 同类：都是词面。在已经融合过的列表上再数交集，接近弱化版 BM25，对同义、口语、步骤近邻（折叠 vs 展开）帮助很小，还可能抬高堆了相同二字的无关段。交叉编码器看的是「这对文本是否在回答该问」，能处理用词不同但意思对的块。

### 3、解决方案

词重叠最多当无模型时的占位，不要当成精排已经做完。要真精排就上交叉编码器（或同类相关模型）：批量推理、截断正文长度、超时回退到融合顺序。用 Hit@1 看效果：真精排时 Hit@k（宽窗口）往往几乎不动，Hit@1 上升；只有词重叠时两者都可能几乎不动。

### 4、这样做的目的和效果

避免「开了 rerank」但排序质量不变的假进展。小语料上模型精排也可能收益有限，要用混淆样本（近义操作、相邻章节）验证，不要只看平均 Hit@k。

## 把召回从 20 条加到 100 条，延迟主要涨在哪？怎么控？

### 1、问题背景

为了少漏检，想把每路候选和精排输入都加大。担心问答变慢，却说不清慢在检索、精排还是生成。

### 2、原因

问句 embedding 一般一次，与候选条数无关。向量检索在未建 ANN 的中小库上是扫全表再取 `limit`，`limit` 从 20 到 100 通常很便宜。内存 BM25 本来就对全库打过分，多取几十条可忽略。RRF 是内存算术。

交叉编码器近似按**精排条数**线性变贵，且每对正文越长越慢。生成模型往往仍是整句最长的一段。把「召回宽度」和「精排条数」绑在一起加，会把时间花在精排上，却误以为是「检索 100 条」本身贵。

### 3、解决方案

拆开两个旋钮：召回窗口只管漏不漏；精排条数管准和延迟。先定精排时延预算，再定条数。多对一次批量推理，禁止一对一次 HTTP。精排只送问句加正文前一段（能判断是否答上即可），不要喂整块上限 token。超时则用融合顺序截最终条数继续生成。闲聊或首位相关分已明显高于其余时，可以跳过精排。

### 4、这样做的目的和效果

漏检用召回窗口治，混淆用精排治，慢用精排条数和截断长度治。不会出现「为了准把 100 段全文都过 rerank」这种账单。

## 精确匹配旁路（FAQ / KV）为什么不要再向量化进主库？

### 1、问题背景

短事实（字段值、FAQ）已经有精确匹配存储。为了「一份库」，会把这些键值再切成块、编进向量索引。面试会问：是不是两套库就一定要双写。

### 2、原因

精确匹配要的是键对上就返回，不能「意思近」。编进向量库之后，近邻会把相近问题的答案挤在一起，FAQ 的确定性丢了。入库还要维护两套切法：知识块按段落切，KV 按字段切。查询侧若默认走向量，精确路径等于没接。主路径没有启用时，为旁路预埋第二套必建库，写入和迁移都会分叉。

### 3、解决方案

知识块向量库常驻。精确匹配只在插件启用时存在：吃可分块原文，不吃切好的块；命中则短路，返回同一形状的检索命中。关掉则当未命中，直接走知识块。不要把 KV 再编进向量库。不要为了完整而默认双写。

### 4、这样做的目的和效果

FAQ 保持可预测。主路径对象形状不因旁路开关而变。代价是启用时多一条短路逻辑，必须和过滤共用同一套筛选，否则点名某来源仍可能命中别的 FAQ。

## 引用为什么由程序从命中填写，不让模型在答案里自编出处？

### 1、问题背景

提示词写「请列出参考文献」。模型有时编页码、把两段合成一个来源、或引用窗口里根本没有的文档。侧栏「参考资料」若跟模型输出走，会和检索对不上。

### 2、原因

生成模型的任务是写答案，不是当数据库。出处是检索命中上已经有的 id、来源、页、摘录。让模型再抄一遍，等于把结构化字段重新变成自然语言再解析回来，中间必然丢。引用对象应和进 prompt 的那几条命中同一份，评测和排障才能对窗口。

### 3、解决方案

程序用本轮命中组装 `citations`（id、来源、页、snippet）。模型只写 `answer`。界面侧栏绑定这份列表，由用户点哪条答案决定看哪一次引用，不跟在气泡下面当模型附件。不要从答案文本里正则抽「第 X 页」。

### 4、这样做的目的和效果

出处可点、可测、不胡编页码。代价是模型不能「灵活」合并来源；步骤跨两块时，要靠分块/父块回填让窗口里真有那些段，而不是让模型假装看见了。

## 过滤

## 第一份样本是某领域文档，为什么不能把该领域字段写成库的过滤合同？

### 1、问题背景

先拿汽车手册把链路跑通，表上就有「品牌」「车型」两列，提示词也按汽车写。下一份文档是合同或课程讲义时，这两列要么空、要么被硬填成无关值。面试会问：过滤维度是产品设计还是样本泄漏。

### 2、原因

合同字段一旦进表列、进请求体、进提示词，整条链都按「库里永远有这两个键」写。过滤、意图、前端芯片都会假设键名固定。样本领域不是库的领域：任意文档能抽到的键不同，有的文档抽不出领域标签。把第一份样本的键写死，等于把「碰巧抽到的属性」升级成系统定义。

### 3、解决方案

文档身份用每份都有的来源（文件 stem、URL 等），可筛。过滤标签用入库时从正文抽出的 `{字段名, 值}` 列表，字段名不预置、可空。查询只对照库里已经出现过的对做硬切，多对 AND，空则该维不限。手册仍可抽出品牌和车型，只是两条普通标签。不要把来源再写进标签列表，身份和标签分开。提示词不要假定某个行业。

### 4、这样做的目的和效果

换文档类型不必改表结构和提示词。代价是标签形状不固定：向量库往往存成 JSON 字符串，列过滤不如固定列好写；意图要从目录里选对，不能靠枚举几个空串。

## 来源和过滤标签为什么要拆开，而不是都当标签？

### 1、问题背景

有人主张「来源也是一条标签」，查询侧只维护一张标签表。也有人把文件名和领域属性摆成并列的筛选项。

### 2、原因

来源是文档身份：每份输入都有，用来替换写入、引用出处、点名「就问这一份」。过滤标签是从正文抽的属性，可有可无、键随文档变。两者语义不同：身份缺失是入库事故；标签为空只表示「这维不限」。把来源塞进标签，点名文档和点名属性会混成同一套匹配；意图模型也容易把文件名再抽成一条假标签。

### 3、解决方案

查询合同分成两维：来源空串表示不限文档；标签空列表表示不限属性。展示时可以把来源画成芯片，那是界面，不是把来源写进知识块的标签列。入库抽标签时明确禁止写入来源身份。

### 4、这样做的目的和效果

替换写入、引用、点名文档走身份；收窄领域走标签。前端可以同一排芯片，后端不要同一套字段。

## 标签硬切之后，为什么向量近邻可能一条都留不住？

> 本节记的是 ADR-0026 时代的做法（标签硬切）。ADR-0035（2026-10-10）起标签只做**加权**、不硬切，本节留作面试素材，不要照它改代码。

### 1、问题背景

过滤从固定列改成动态键值后，向量检索仍先取全局 top-n，再丢掉不含这些标签的块。过滤很严或相关块很少时，近邻列表和过滤后的集合可能没有交集，看起来像「库里有、检索却空」。

### 2、原因

ANN / 表搜索的 `limit` 是在未过滤或只按少量列过滤的空间里取近邻。动态标签常常整段 JSON 存在一列，不好写成高效 `where`。先搜再滤，等于在错误的候选集合上截断。文档级标签（一份源的所有块标签相同）时，标签硬切其实等价于「只保留若干来源」；若不把来源集合推回检索，向量路仍在全库里挤名额。

### 3、解决方案

先按标签算出允许的来源或 id 集合，再在这个集合里做近邻和 BM25。来源能进 `where` 就进；id 太多不宜 `IN` 时，至少按匹配到来源列表收窄。过滤后集合为空要早退，不要带着空集合去搜。不要指望加大 `limit` 长期补救，库一大仍会漏。文档级标签复制到每个块上，是为了命中仍带标签，不是为了按块做不同硬切。

### 4、这样做的目的和效果

硬切真的作用在检索空间上，而不是只作用在已经截断的名单上。代价是实现比「搜完再 if」多一步；标签若将来变成块级而不是文档级，还要有按 id 收窄或把可过滤字段提成列。

## 过滤层和图上的 filter 节点是一回事吗？

### 1、问题背景

架构图画了「标签过滤层」，编排图却只有 intent → recall → rerank → generate。有人主张再加一个 filter 节点，否则「层」是假的。

### 2、原因

**层**是职责落点：谁产生 filters、谁按标签收窄集合。**图节点**是一次请求里要不要单独停一站。过滤的 match 发生在查库内部（先筛再搜），没有独立的「过滤结果对象」要交给下一站——下一站要的是命中列表。多一个节点只是把 `search` 里的一行调用抬到图上，不改合同。

### 3、解决方案

保留过滤层（空过滤、filters 形状、match）。图上不设 filter 节点；召回 `search` 调用 match。意图节点负责给出本轮 filters。向面试官说明：层目录和图拓扑不必一一对应。

### 4、这样做的目的和效果

层可测（match 单测、intent 出 tags），编排保持短。避免「为了图好看拆节点」和「没有节点所以没有层」两种假对立。

## 评测与完整证据

## 改召回、改写、精排之前，为什么要先有评测？评什么？

### 1、问题背景

线上已经能答，但口语问句、题外话、步骤答串题时，会想直接改改写提示词或换精排模型。没有固定样本时，改完只能靠手问几句。

### 2、原因

问句改写可能把本来能命中的规范问句改坏。相关度阈值可能把正样本拒掉。精排可能只换座位、不提高命中。这些都是「有时变好、有时变差」。没有正样本（该命中哪份文档 / 哪一页）和负样本（不该答），无法证明是检索问题还是生成问题，也无法做开关对照。

### 3、解决方案

用最小评测集，且评的是**生成实际能看见的那几条**，不是召回内部的大窗口：

- 正样本：规范问句 + 口语 / 同义问句。指标常用 Hit@1 / Hit@k（期望来源或页是否出现在最终窗口）。
- 负样本：知识库不该覆盖的问题。看是否拒答或相关分是否够低。
- 改某一层时只开那一层，和关闭状态比同一套样本。

评测可以不调生成：先确认证据在不在窗口里。答案完整、是否串题是下一层（生成 / 父子块），不要只用 Hit@k 当全部。

### 4、这样做的目的和效果

把「感觉更准」变成可回归的对照。坏改写、过严拒答、无效精排能在上线前暴露。评测窗口必须和线上 prompt 窗口一致，否则在宽窗口上算分、线上只用前几条，结论是假的。

## Hit@k 过了，是否说明模型会用上前 k 条，而不会只盯第一条？

### 1、问题背景

口语问句的正确答案有时排在第 2～k 位。有人把 Hit@k 理解成：「如果精排把准答案排前面，模型才会用；排后面模型会忽视。」于是用 Hit@k 去证明生成侧的注意力，或把「未进第 1 位」说成评测失败。

### 2、原因

Hit@k 是检索指标：期望证据有没有出现在**生成实际能看见的那 k 条**里，以及排第几。它不观察模型读 prompt 时看了哪几段。生成模型拿到的是窗口里的全部摘录；会不会偏信第一条、会不会忽略后面，是生成 / 提示词问题，评测若不调生成，就不可能知道。把后面没跑的阶段写成测试目的，会把「排位差」和「没召回」混成一种失败，也会把「该加大窗口 / 该上精排」和「该改生成」混在一次对照里。

### 3、解决方案

评测顺着线上链路走到生成窗口成形为止（改写、召回、截断、若有邻块回填也算进窗口），立刻判命中，不调生成。正样本：证据在第 1 位记 Hit@1，在第 2～k 位只记 Hit@k。通过与否以「进不进窗口」为准；第 1 位另报，用来看精排有没有把对的人排到最前。负样本看会不会在生成前拒答。要测模型是否偏信第一条，另做生成侧样本（例如窗口里第 1 条干扰、后面才是证据），不要改写 Hit@k 的含义。

### 4、这样做的目的和效果

检索对照和生成对照拆开。口语问句「进了窗口但没排第一」是排位问题，不是评测没过，也不是已经证明模型会看后面。面试里能分开「证据在不在 prompt」和「模型读 prompt 时怎么用」。

## 正样本的 Hit@k 为什么不能只对「哪份文档」，还要对页或块？

### 1、问题背景

最小评测常写成：问句命中期望来源就算过。一本手册入库后有成百上千块，很多块都带同一个来源。口语问句可能捞到「来源对、章节完全错」的块，Hit@k 仍然全绿。

### 2、原因

来源只回答「是不是这本书」。操作类问题真正要的是某一页或某一标题下的段。只对来源，等于在全书范围里开卷考试：洗涤液、轮胎、后视镜都算「手册命中」。后面的精排、邻块回填、生成都会在错误章节上显得「有引用」。页码是阅读器页，和切块边界可能不完全重合，但对「是不是这一段」比来源严一个数量级。

### 3、解决方案

正样本同时钉文档身份和页（或块 id）：命中的来源要对，且页集合与期望页有交集。没有页的源才退化为只对来源或对块 id（本阶段入库只收 PDF；抽不出印刷目录的来源 `pages` 会是空，见 TODO P2·13）。负样本仍然不看来源，只看拒答。样本问句要覆盖：规范问法、口语同义、以及「来源对但容易串到相邻章节」的混淆句。

### 4、这样做的目的和效果

串题会在评测里变成没过，而不是「有引用就算准」。代价是标注要翻原文记页；切块规则变了，期望页可能要跟着核一次。

## Hit@k 已经过了，答案仍残或缺步骤，还缺什么？

### 1、问题背景

评测显示期望来源或页已在前 k 条，但模型只答了半个操作，或缺前后步骤。有人继续加大 k 或换 embedding。

### 2、原因

Hit@k 只说明**有一块相关文字进了窗口**，不说明窗口覆盖了答完这问所需的全部上下文。按标题或固定长度切块时，步骤常跨相邻块。检索命中的是最像的那一小节，生成看不到上一节的前提或下一节的收尾。这是分块与上下文扩展问题，不是「向量还不够近」。

### 3、解决方案

常见做法：父子块（子块检索、父段进 prompt）；按目录标题把同节邻块并进窗口；或检索后向左右扩展页 / chunk。必须给合并设上限，防止整章塞满上下文。用「步骤是否完整」的生成侧样本看，不要只用 Hit@k。

### 4、这样做的目的和效果

证据完整，操作类答案不易半截。代价是 prompt 变长、生成更慢。和精排正交：精排决定哪几条进窗口，父块回填决定每条周围带多少。

## 系统边界

## 「检索门面」到底是查库口还是前端页？没有 UI 的 RAG 还算不算完整？

### 1、问题背景

「门面」在代码里常被用来称呼检索 API。产品里又有对话页、侧栏引用。面试会把「系统」和「页面」问成同一个东西。

### 2、原因

查库口是后端：过滤 + 召回，HTTP、编排图、命令行脚本共用。对话页是独立前端进程，只调提问接口做展示（主栏答案、侧栏引用）。若把查库口叫门面，会以为没有页面就不能问；若把门面理解成 UI，又会以为检索 API 是页面的内部函数。侧栏「参考资料」只是引用的界面文案，对象仍是生成结果里的 citations。

### 3、解决方案

三个名字分开：查库叫召回层（内部先过滤）；提问口是薄 HTTP（或调试脚本）；独立前端只展示。没有前端，接口和脚本仍能走完整在线路径。

### 4、这样做的目的和效果

评测可以不启前端。换皮肤不改检索。面试里能说清 RAG 引擎和对话壳不是一层。

## 检索评测、单轮生成、多轮会话，为什么不能合成一个调试脚本？关着的实验入口算不算主路径？

### 1、问题背景

线上链路是意图 → 召回 → 精排 → 生成。调试时会想要一个入口「什么都能测」。另一边，精确匹配、另一种切法往往还留着几百行实验脚本，和人对库的入库脚本并列，分不清还要不要跑。

### 2、原因

三件事停在不同位置，失败原因不同：

- 检索评测：证据在不在生成窗口、会不会误拒。不调生成，才能和改写 / 截断 / 邻块做对照。
- 单轮生成：窗口之后模型写不写得对。没有会话，测不了跟进、筛选沿用、闲聊切回检索。
- 多轮会话：同一会话 id 下 turns 只给意图。必须循环提问、固定会话，才能看到「它怎么展开」会不会串题。

合成一个脚本，要么评测被生成延迟拖慢，要么「跑一遍」没有会话历史却以为测了多轮。关着的实验入口（精确匹配抽键值、旁路写库）不走现行抽取合同，和生产入库是两条路；查询侧插件未启用时，跑它不会改变主路径行为，只增加第二套写库和重复的抽正文。

### 3、解决方案

调试口按停点拆：最小评测只到生成窗口；单轮改一句话、跑完即退、看答案和引用；多轮固定会话、循环输入。长驻提问口继续走 HTTP 和页面。实验脚本标明不是生产入库，主路径关着就不跑；插件若长期不开，再单独立项删，不要每天当必跑步骤。不要把实验档的「另一种写库」当成入库的快捷方式。

### 4、这样做的目的和效果

检索回归快，生成手测清，多轮指代有会话。主闭环不会被停机实验拖成双写。代价是入口多几个文件，使用说明必须写清各测什么。
