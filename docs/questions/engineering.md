# 工程与文档面试问答

从「项目结构、配置分类、README 写什么」这一轮保持一致的工作里抽出的面试题。给以后被问到工程规范时用。检索流程题见 [README.md](README.md)。实现细节以 [目标架构](../architecture.md) 和 ADR 为准。

按**现形态**编排。早期做法（host/port 进 yaml、路由和进程焊在一个文件、未验证开关写成使用说明）写在对应题的原因里，不当现行方案。

每条结构：问题背景 → 原因 → 解决方案 → 目的和效果。

---

## 项目配置为什么不能全塞进一份 yaml？

### 1、问题背景

常见做法是一个 `config.yaml` 里同时写项目根路径、host/port、外仓 URL、甚至别人家 `.env` 的盘符路径。换机器或上生产后，文件要么改不完，要么把密钥带进仓库。

### 2、原因

这几类东西的**变化原因不同**：

- 根目录随本机盘符变，写死盘符必错。
- 本服务监听地址本地几乎不改，生产常由镜像 / 编排注入。
- 第三方地址、密钥随对接环境和人变，进 git 会泄漏。
- 相对数据目录、模型目录名在各环境相同，才适合进仓的公共文件。

混在一份 yaml 里，改一类就会误伤另一类，审查也分不清「能提交」和「绝不能提交」。

### 3、解决方案

按变化原因分开：

- 从本机推算的值（项目根、把仓库根加入模块搜索路径）写在一处基础模块，启动文件引用，不要每个入口再抄一遍。
- 本服务 host、port 写在启动文件。生产用镜像覆盖。
- 第三方对接地址和密钥只放根目录 `.env`，模板进仓。不要在 yaml 里指向另一份带密钥的 `.env`。
- 进仓的 yaml 只放各环境相同的本项目常量。

### 4、这样做的目的和效果

换电脑不用改配置文件。密钥进不了仓。启动文件一眼能看出这个进程绑哪。面试里能说清「配置」不是一种东西。

## 长驻服务的启动文件为什么放在仓库根？一次性脚本为什么另放？

### 1、问题背景

实现写在子包之后，会习惯用包内入口或 `python 子目录/xxx.py` 起进程。路由下沉到 `router.py` 之后，又会问：是不是改成直接跑路由文件。下载权重、入库、评测也容易和长驻 HTTP 挤在同一个包目录里。

### 2、原因

人跑服务时要记住的是「哪个文件等于哪个进程」，不是「哪个包碰巧能当入口」。包内入口和根上启动文件并存时，两套生命周期、两套 host/port，改一处漏一处。`python 子目录/xxx.py` 还会把工作目录搞乱，相对路径和项目根推算对不上。

「路由写在哪」和「进程从哪起来」是两件事。路由文件提供路由表，没有端口、没有生命周期。下载、入库、评测跑完即退出，和长驻服务不是同一类入口；放进服务实现目录，会让人以为下载会拉起 HTTP。

### 3、解决方案

单服务根目录 `main.py`；多服务根目录 `服务名_server.py`。启动文件只创建应用、写 host/port、挂路由、注册生命周期（例如启动时打开知识库）。业务实现和路由放架构层。同一个进程不要在包内再留一份入口。跑完即退出的入库、下载、评测、调试放脚本目录。日常不要用子目录里的路由文件起服务。

### 4、这样做的目的和效果

使用说明的启动列表和磁盘上的文件一一对应。层目录只放实现，不兼作入口。「起服务」和「准备权重 / 入库」是分开的两步。面试里能把「模块边界」和「进程边界」分开说。

## README 该写什么？目标架构文档、计划、视觉规范各管什么？

### 1、问题背景

一个仓里同时有 README、architecture、ADR、TODO、DESIGN。容易把「怎么跑」「为什么这样设计」「还没验证的方案」「页面交互」全写进 README。结果要么太长没人读，要么方案一变 README 就过期。

### 2、原因

读者打开 README 是要**跑起来并确认没坏**。目标架构文档回答目标态和明确不做。计划回答「还没对照实验、当前暂定什么」。视觉规范回答会随需求改的交互。把未定方案写成使用步骤，读者会当成已拍板；把前端边界写成 README，需求改一次文档就谎一次。

### 3、解决方案

README 固定四块，每块分开，不要揉成一段：

1. 系统名称；名称下直接写做什么；设计原型每条一个标签加链接（有文件才链）。
2. 生产地址（未部署写本地）、代码托管（没有写「无」）；启动前最少准备；有几个长驻服务写几个启动命令；依赖谁、要什么密钥。
3. 关键目录树 + 层/模块各做什么。
4. 使用说明：当前设计下输入输出和命令；可复制的主路径测试和预期；脚本目录哪个文件测哪一层。

还没验证的方案写进计划：目前还未验证出最准确、稳定的方向，当前暂定 xx，候选有哪些。前端易变边界写视觉规范 / 目标架构文档「明确不做」，不进 README。源文件会变，不要把具体文件名写死；当前实现写「当前用 xx」。

### 4、这样做的目的和效果

README 可当验收清单。方案研究不影响「怎么启动」。面试里能分开「给使用者的约定」和「给自己的实验记录」。

## 使用说明里，怎样测「系统跑通了」，而不是只贴启动命令？

### 1、问题背景

README 写完启动命令之后就结束。新人能把进程拉起来，不知道输入放哪、成功长什么样、问答页先问什么才算对。

### 2、原因

启动成功只说明端口在听。离线要看抽取和向量有没有写进磁盘；在线要看意图、单轮检索、多轮指代是不是按设计走。没有可复制的输入和预期，测试会变成「随便问一句看看像不像」。

### 3、解决方案

使用说明写在项目结构后面，至少三件事：

- 入库：输入目录、命令、输出各是什么（可分块原文、知识块、向量库）。
- 主功能手测：可复制的句子 + 预期。先闲聊确认不检索；再问一条知识问题确认有引用；再问指代不明的跟进，且写明同一会话、不要刷新；若系统有文档身份，再问「资料来源 / 哪份文档」，确认不会判成闲聊。
- 层测试：脚本目录里哪个文件对应离线整条、在线检索最小评测、带生成的单轮、同一会话的多轮。没有单独脚本的层如实写「走页面」，不要编测试文件。关着的实验入口不要写进「怎么测跑通」。

未定实验入口不写进这一节。

### 4、这样做的目的和效果

读者能自己对照「闲聊无引用 / 单轮有引用 / 跟进仍指上一轮 / 出处追问仍检索」。评测脚本测检索窗口，单轮脚本测一次生成，多轮脚本测会话，页面测完整对话，职责不混。

## 还没验证的查询手段，为什么不能写成 README 里的「开关说明」？

### 1、问题背景

在线路径上往往留着改写、重排、拒答、精确匹配短路等开关。为了「文档完整」，会在 README 里列一张表：默认开或关、改完重启。面试或新同事会把它读成已定架构。

### 2、原因

这些开关回答的是「怎样查询更准」，需要对照实验，不是启动步骤。默认关着的项写进 README，读者会以为应该去拧。已经用评测写死的手段（混合检索、改写、按相关度拒答、召回吐出候选窗口再由重排截到生成窗口大小）属于当前设计，应写进目标架构文档和使用说明的预期，而不是一张「可随便拨」的开关表。仍未验证的（词重叠重排、精确匹配短路、交叉编码器）才是计划里的候选。

### 3、解决方案

README 不列实验开关。计划里写：目前还未验证出最准确、稳定的方向；当前主路径是什么；候选还剩哪些。代码常量可以留在实现文件里，改完重启服务，但这是实现细节，不是使用指南。真正拍板后再改使用说明和目标架构文档的状态。

### 4、这样做的目的和效果

避免把实验台状态当成产品约定。读者按使用说明手测的是现行流程，不会去拨未验证的旋钮。

## 决策改了，为什么不改写旧 ADR，而是另开一条给它开例外？

### 1、问题背景

先决定路由和进程同放一个文件，后来改成启动文件加路由模块。先决定 host/port 进 yaml，后来改成写在启动文件、第三方进 `.env`。会想直接改旧 ADR 正文，让文档看起来「从来如此」。

### 2、原因

ADR 记的是当时为什么选。改写决策段等于伪造历史：后人看不到曾选过的形态，会把现行文件当成唯一合理形状，再「修」回去。旧标题可以保留当时用词；变的是文末现状。目录规范是默认，仓库后写的决策可以覆盖先写的位置；已按离线/在线/共享服务切过的仓，不必为了「前后端分离范本」整仓搬进 `backend/` + `frontend/`。

### 3、解决方案

够格再记新 ADR（难逆转、否则费解、有真实备选）。新条写明给哪几条开例外。旧条不删、不改当初的选定句，只补现状并链到新条。读的时候一组一起读。规范用在缺口上：保持一致还不打架的几条（启动文件命名、配置分类），不拿来推翻已拍板的层的位置。

### 4、这样做的目的和效果

排障能顺着编号看到「为什么现在不是当初那个文件名」。面试里能区分「决策」「当前磁盘状态」和「通用目录规范」。

## 项目根已经写在基础模块里，为什么脚本目录里的入口还要先改模块搜索路径？

### 1、问题背景

规范要求项目根和把仓库根加入模块搜索路径只写在一处基础模块，启动文件引用、不要每个入口再算一遍。脚本仍常见几行：先把上一级目录插进搜索路径，再 import 配置包。看起来像配置分类失败。

### 2、原因

从仓库根启动长驻服务时，解释器把仓库根放进模块搜索路径，配置包直接能 import，基础模块再保证项目根在路径里。从脚本目录启动时，解释器把脚本所在目录放进搜索路径，此时还 import 不到配置包，里面的项目根用不上。这是解释器怎么定位脚本目录，不是「根常量写了两份」。

### 3、解决方案

根上的启动文件直接 import 配置。脚本目录里只插「脚本的上一级目录」以便找到配置包，不要在脚本里再赋一个盘符路径当事实源。插完立刻从基础模块读项目根。层模块不要自己改搜索路径，假定入口已经做过。

### 4、这样做的目的和效果

项目根仍只有一处推算。脚本能从子目录启动，又不把盘符写进 yaml。面试里能说清「import 引导」和「项目根常量」不是同一行代码。

## 入口脚本的文件头为什么要按系统流程写，并且原理编号和入口编号要分开？

### 1、问题背景

评测或调试脚本一打开就是函数列表。读的人把「入口第 2 步」当成「一条样本在系统里的第 2 步」，或把脚本没跑的阶段（生成、模型会不会只看前几条）写成测试目的。面试会问：脚本说明书该写什么，写到哪一层算清楚。

### 2、原因

一条样本在系统里走的步，和打开这个文件从哪几个函数进，是两套序列。都从 1 数、又不声明，读者会把「开库、逐条检查」理解成「召回、重排」。原理若写成抽象指标定义，系统流程要到例子才出现，指标和流程对不上。例子若另起概念，文件头会变成第二份设计文档。没跑的阶段写进开场当测试目的，评测口和生成口的职责会焊在一起。

### 3、解决方案

文件头分层，缺一层再补。真·一步脚本可以只留开场和怎么跑。

1. 一句：干什么、停在哪、不干什么。
2. 原理：先写完整流程，再写本脚本每条样本走到哪、立刻判、然后下一条。正负样本分写。测到哪写到哪。
3. 例子：用本文件会跑的输入把原理走一遍；一次实测要标明会变；分清过、没过、过了但不够好。
4. 怎么跑：职责、入口函数、输入、前置、产出、对外。标题写明这套编号和「一条样本」不是同一套；入口函数映射回原理第几到第几步。

不要把范本放在别的仓库里用路径去够；完整例子和写法规范放在一起。

### 4、这样做的目的和效果

打开文件先读头，就能回答测什么、不测什么、从哪进。排位差不会被读成评测没过。代价是文件头变长；业务指标不要整段搬进别的脚本，搬的是层次。
